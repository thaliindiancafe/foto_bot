## Что это за проект

Telegram-бот для контроля персонала через фоточек-листы.
Сотрудники проходят чек-листы, подтверждая каждый пункт фотографией.
ИИ проверяет фото на соответствие задаче. Данные уходят в Google Sheets.

---

## Главный приоритет

- Быстрый стабильный MVP без переусложнения
- Не добавлять функционал которого нет в требованиях
- Это чек-лист бот, не CRM и не платформа

---

## Стек

- Node.js + TypeScript (strict)
- Telegraf (Telegram Bot API)
- SQLite через Prisma (MVP)
- S3-совместимое хранилище (Cloudflare R2 / Yandex Object Storage)
- Google Drive — опционально, только если включён флагом ENABLE_GOOGLE_DRIVE=true
- Google Sheets через Make webhook (HTTP POST)
- OpenAI gpt-4o-mini для проверки фото
- Sharp для наложения водяного штампа на фото

---

## Границы MVP (не выходить за них)

1. 8 должностей — берутся из src/config/checklists.json
2. 4 типа чек-листов: open, periodic, close, manual
3. Каждый пункт чек-листа требует фото
4. Один активный чек-лист одного типа на пользователя
5. Состояние хранится в БД, не в памяти
6. Админ-панель как UI — НЕ входит в MVP
7. Управление чек-листами — через конфиг (JSON) или импорт
8. Команда /reload — только для администраторов (из ADMIN_IDS)

## Логика FSM

```
/start
  → не зарегистрирован: запрос имени → выбор должности
  → зарегистрирован: меню чек-листов по роли и времени

Старт чек-листа:
  → создать run
  → показать первый вопрос

Получено фото:
  → наложить штамп (имя + дата + время) через Sharp
  → загрузить в S3
  → AI-проверка если задано ai_rule
  → сохранить verdict в answers
  → POST в Make webhook
  → следующий вопрос

Завершение:
  → закрыть run
  → если тип close → рассчитать смену (shifts)
```

## Расчёт смены

- Начало смены = время первого фото с verdict "ok" по правилу uniform_check в чек-листе open
- Конец смены = время завершения чек-листа close
- Итог записывается в shifts: minutes (отработано), fail_count (количество неверных фото)
- fail_count влияет на расчёт зарплаты (формула на стороне Google Sheets)
- Ежемесячная статистика суммируется в отдельном листе таблицы

---

## Расписание чек-листов

- open — отправляется в начале смены (время из конфига)
- close — отправляется в конце смены (время из конфига)
- periodic — отправляется каждые 2 или 3 часа (интервал из конфига)
- Расписание реализовать через node-cron
- Если пользователь не прошёл чек-лист в отведённое время — фиксировать пропуск

## Защита от намеренного саботажа сотрудниками

Сотрудник не должен иметь возможность "сломать" бота чтобы избежать фотофиксации.

### Спам и флуд
- Текстовый спам в момент ожидания фото — игнорировать, отвечать коротко: "Пожалуйста, отправьте фото"
- Не падать и не зависать от любого количества входящих сообщений
- Обрабатывать все входящие через try/catch — любая ошибка логируется, бот продолжает работу

### Попытки сбросить состояние
- /start в середине чек-листа — НЕ сбрасывать активный run, показать текущий вопрос
- Повторный /start — показать что чек-лист уже в процессе и предложить продолжить
- Нельзя отменить начатый чек-лист без участия администратора

### Отправка неверных файлов
- Документ не являющийся изображением — отклонить: "Отправьте фото, не файл"
- Видео, стикеры, голосовые сообщения — игнорировать
- Слишком маленькое фото (менее 100x100px) — отклонить, попросить нормальное фото

### Блокировка бота
- Если сотрудник заблокировал бота — фиксировать пропуск чек-листа автоматически
- Ошибка "bot was blocked by the user" — обрабатывать gracefully, не падать
- Разблокировка бота — сотрудник продолжает с текущего активного вопроса

### Манипуляции со временем
- Все временные метки фиксировать на стороне СЕРВЕРА, не доверять времени от клиента
- Время штампа на фото = время получения фото сервером, не время отправки пользователем

### Фиксация всех действий для администратора
- Логировать: пропуски, отклонённые фото, попытки спама, блокировки бота
- В Google Sheets фиксировать статус каждого чек-листа: пройден / пропущен / в процессе
- Пропущенный чек-лист = отдельная строка со статусом "missed" и причиной
- Администратор всегда видит полную картину — даже если сотрудник "ничего не делал"

## Надёжность и защита от саботажа

### 1. Rate limit (anti-spam)
- Не более 10 входящих сообщений в минуту от одного пользователя
- Не более 5 фото в минуту от одного пользователя
- При превышении: отвечать "Слишком часто. Подождите 30 секунд" и игнорировать лишнее
- Счётчики хранить в памяти (Map с TTL), не в БД — для скорости

### 2. Идемпотентность записи в Google Sheets
- Не допускать дублей при повторных попытках отправки
- Ключ идемпотентности: run_id + question_id
- В таблице answers добавить поле sent_to_sheets: boolean
- Если sent_to_sheets = true — повторно не отправлять ни при каких условиях

### 3. Outbox-паттерн для внешних интеграций
- Любая отправка во внешние сервисы (Make webhook) идёт через таблицу outbox в БД
- Схема outbox:
  ```
  id, event_type, payload_json, attempts, next_retry_at, status (pending/sent/failed), last_error
  ```
- Порядок при получении фото:
  1. Сохранить ответ в answers
  2. Добавить событие в outbox со статусом pending
  3. Попытаться отправить немедленно
  4. Обновить статус outbox
- Фоновый воркер (setInterval или node-cron) повторяет отправку pending событий с учётом next_retry_at
- Система работает даже если Make webhook временно недоступен — данные не теряются

### 4. Retry на временные ошибки
- Make webhook: до 3 попыток с exponential backoff (1с → 2с → 4с)
- Повторять при: HTTP 429, HTTP 5xx, сетевые таймауты
- При окончательном fail:
  - outbox.status = failed
  - логировать ошибку с correlation id
  - основной сценарий пользователя НЕ ломать
- AI и Storage: 2 попытки с паузой 1с, при fail — сохранить в БД, продолжить без блокировки

### 5. Таймауты и статусы для пользователя
- Установить таймауты:
  - Storage upload: 15 секунд
  - AI check: 20 секунд
  - Make webhook POST: 10 секунд
- Пользователь всегда получает ответ:
  - Сразу после фото: "Фото принято, идёт проверка..."
  - После проверки: "✅ Шаг засчитан" или "❌ Нужно переснять"
  - При ошибке внешних сервисов: "Фото сохранено, данные будут отправлены позже" — и продолжить
- Никогда не оставлять пользователя без ответа более 30 секунд

### 6. Команда /status для администратора
- Доступна только telegram_id из ADMIN_IDS
- Показывает диагностику кратко:
  ```
  🟢 DB: ok
  🟢 Storage: ok
  🟡 AI: slow (2.3s avg)
  🔴 Make webhook: fail (last error: timeout)
  📬 Outbox: pending 3, failed 1
  ```
- Нужна для быстрого ответа на заявления сотрудников "бот не работает"
- Если всё зелёное — значит бот работает, проблема на стороне сотрудника

### 7. Логи и аудит
- Логировать ключевые события с полями:
  ```
  user_id, role, run_id, question_id, step_state, timing_ms, error_code
  ```
- Все ошибки писать с correlation_id (run_id) для быстрого разбора
- Уровни логов: info (штатные события), warn (нештатные но не критичные), error (сбои)
- Логи хранить в файл с ротацией (winston или pino)

### 8. Защита админ-доступа
- Список администраторов хранить в ADMIN_IDS в .env
- Проверку на админа делать middleware-ом, не в каждом хендлере отдельно
- Неадмин получивший админ-команду — логируется как подозрительное действие

### Главное правило надёжности
Система продолжает работу даже если временно недоступны AI / Make / Storage.
- Данные сначала в БД, потом во внешние сервисы
- Сбой внешнего сервиса = пометка в outbox, догрузка позже
- Пользователь не блокируется из-за внешних сбоев

    - `Пропустить` исключает пункт из знаменателя расчёта;
    - итоговый процент чек-листа = сумма набранных весов / сумма учитываемых весов;
    - на дашборде отклонением считается чек-лист с результатом `< 90%`.
12. По скриншоту редактирования пункта подтверждены настройки:
    - `Фотография обязательна`
    - `Видео обязательно`
    - `Можно пропустить`
    - `Автоматически создавать задачу при ответе "Нет"`
13. По присланным материалам пока НЕ подтверждено, что Service Inspector автоматически сравнивает фото с эталонным изображением; на текущий момент доказана обязательность наличия фото, но не найден подтверждённый механизм автоматического image-to-image сравнения.

### Ждём от клиента


1. **Эталонные фото** — ко всем чек-листам нужны фото, ждём оставшиеся
2. **Выбор AI-провайдера** — пока бот на ключе OpenAI, клиент должен определить финальный AI-стек

### Запланированные функции после эксперимента
1. **Фото-контроль качества через AI** — расширить текущую проверку фото до полноценного AI-аудита зон ресторана:
   - форма сотрудника;
   - чистота зала;
   - чистота туалетов;
   - чистота кухни;
   - кофемашина;
   - витрины;
   - выкладка;
   - заполненность станций.
2. Это не должно быть просто "ещё одним отчётом". Ценность функции — в операционном контроле: бот подсвечивает подозрительные моменты сразу после прохождения чек-листа, чтобы команда могла быстро исправить проблему.
3. **Контроль нарушений и задач** — если сотрудник ответил `Нет`, AI нашёл проблему или менеджер подтвердил нарушение:
   - система создаёт задачу/нарушение;
   - сообщение с проблемой уходит в общий рабочий чат, где вся команда видит косяк;
   - сотрудник идёт устранять проблему;
   - после исправления сотрудник отправляет фото "после";
   - менеджер видит не только факт ошибки, но и закрытие проблемы.
4. Для MVP этой функции предпочтителен контрольный режим, а не строгая блокировка: фото/чек-лист можно принять, но нарушение должно попасть в общий чат и остаться открытым до подтверждённого исправления.
5. Важно не превращать это только в отчётность для управляющего. Главный сценарий: чек-лист заполнен → косяки сразу полетели в общий чат → ответственный устранил → задача закрыта.

### UX и формат сообщений (фиксируем требования)
1. **Шорт-лист после чек-листа**:
 - сотруднику после завершения чек-листа приходит краткий итог (шорт-лист нарушений);
 - этот же краткий итог отправляется админам/владельцу (ФИО, должность, чек-лист, короткий список).
2. **Без артефактов Service Inspector**:
 - не показывать пользователю значения `weight` и строки вида `Вес: 50`.
3. **Формат текста вопроса (читаемость)**:
 - заголовок чек-листа — жирным;
 - сам текст пункта — жирным;
 - после текста пункта оставлять пустую строку;
 - инструкцию/описание начинать со значка `ℹ️` и писать курсивом.
4. **Фритюрный журнал для официанта**:
 - удалить чек-лист "Журнал учёта использования фритюрных жиров" из роли `waiter`.

## Style Guide чек-листов (единый стиль для всех ролей)

**Обязателен для всех чек-листов в `src/config/checklists.json`.** Любой новый или
импортируемый чек-лист (manager, waiter, barista, cleaner, cook, helper, sous_chef,
chef) должен проходить этот стайл-гайд, иначе бот покажет неаккуратное «полотно текста».

### 1. Название чек-листа (`name`)

Формат: `<квадрат-эмодзи><цифра-эмодзи> <Роль> — <что это>`.

Цвет квадрата по типу чек-листа:
- 🟥 `open` / `handover_open` (открытие/начало смены) — порядковый номер `1️⃣`
- 🟧 второй открывающий чек-лист / пересменка (`handover_open` №2) — `2️⃣`
- 🟩 пересменка-закрытие (`handover_close`) — `3️⃣`
- 🟦 `close` (закрытие смены / ресторана) — `4️⃣` (или `2️⃣`, если у роли всего 2 чек-листа)
- 🟪 `periodic` / большие чек-листы дня — `5️⃣`

Примеры:
- `🟥1️⃣ Бариста — открытие смены`
- `🟦2️⃣ Бариста — закрытие смены`
- `🟥1️⃣ Менеджер — открытие ресторана`
- `🟪5️⃣ Большая восьмёрка — менеджер`

Не использовать одинаковые названия для разных ролей и не оставлять чек-листы без
эмодзи-префикса.

### 2. Текст пункта (`tasks[].text`) — два блока через `\n\n`

В `text` через **двойной перевод строки `\n\n`** склеены два смысловых блока:

```
<Короткий заголовок-действие>\n\n<Подробная инструкция>
```

Это не косметика, а контракт: бот вызывает `splitTitleAndDescription(text)` и
рендерит первый блок жирным, а второй — курсивом со значком `ℹ️` (см.
`src/bot/index.ts` → `formatQuestionMessage` и `src/services/aiService.ts`
→ `splitQuestionText`). То же разделение использует AI-проверка фото, когда
`ai_rule = null`: title уходит как «Пункт», description — как «Требования и
критерии».

**Заголовок (title):**
- одна короткая строка, без точки в конце;
- описывает действие/состояние («Бокалы натёрты и перевёрнуты»,
  «Селфи в форме у зеркала»), а не процесс;
- без CAPS LOCK, без эмодзи, без `weight` и других служебных артефактов;
- максимум ~80–100 символов.

**Описание (`ℹ️`-блок):**
- обычным языком, как мини-инструкция: что именно проверить, как именно
  сфотографировать, что считается «нормой»;
- допускаются переносы `\n` и нумерованные списки `1) ... 2) ...` внутри блока;
- если список длинный, использовать буллеты `- ` и пустую строку перед/после
  блока в `text` (внутри подразумеваемого описания);
- не дублировать заголовок дословно;
- если у пункта тип `photo` или `confirm_photo` — в описании прямо сказано, что
  именно должно быть на фото («Сделай фото …»).

Минусы, которые ловим на ревью:
- ❌ один сплошной абзац без `\n\n` (рендер ломается, пункт смотрится как стена);
- ❌ заголовок дублирует описание;
- ❌ описание написано в стиле Service Inspector со ссылками `https://drive.google.com/...`
  внутри текста — Drive-ссылки выносим только в `reference_photo`;
- ❌ значения вроде `Вес: 50`, `Важность 5/5` внутри `text` — это служебное.

### 3. Типы пунктов (`tasks[].type`)

| Значение | Когда используем |
|----------|------------------|
| `photo` | требуется только фото; кнопка «Да/Нет» не показывается |
| `confirm` | требуется только подтверждение кнопкой `✔️ Да` / `✖️ Нет`, фото не нужно |
| `confirm_photo` | фото + после загрузки сотрудник нажимает `✔️ Да` / `✖️ Нет` |

Правила:
- если в описании есть фраза «Сделай фото …» — `type` обязан быть `photo` или
  `confirm_photo`;
- если действие нельзя подтвердить фотографией (например, «Прокачать кофемашину
  3 раза» в момент открытия), используем `confirm`;
- `confirm` со скрытым требованием фотодоказательства — антипаттерн.

### 4. `section`

`section` — это группа пунктов внутри чек-листа. Используем понятные русские
названия: «Начало смены», «Подготовка оборудования», «Подготовка бара», «Уборка
бара», «Передача смены», «Окончание смены», «Большая восьмёрка», и т. д.

- `null` оставляем только если у чек-листа реально нет блочной разбивки;
- если разбивка есть — заполняем у всех пунктов чек-листа (без полу-заполненных
  списков).

### 5. `ai_rule`

`ai_rule` — что именно AI ищет на фото (только для `photo` / `confirm_photo`).

- если в описании пункта (`ℹ️`-блок) уже сказано «На фото должно быть …» и этого
  достаточно — ставим `"ai_rule": null`, AI возьмёт критерий прямо из текста;
- если хотим жёсткий короткий визуальный критерий — пишем 1 предложение
  («На фото барная стойка с расставленными чистыми бокалами»);
- **не дублировать** в `ai_rule` целиком текст пункта со всеми инструкциями —
  это раздувает промпт и шумит AI;
- предопределённые ключи (`uniform_check`, `steam_check`, `photo_relevance`, …)
  использовать только если они описаны в `aiService.ts`.

### 6. `reference_photo`

- путь от `src/config/reference_photos/` (например, `"ref_waiter_uniform_selfie.jpg"`);
- ставим только когда эталонное фото реально есть в репозитории;
- если эталона нет — `null` (не выдумывать имена файлов).

### 7. Канонический пример пункта

```json
{
  "order": 1,
  "text": "Селфи в форме у зеркала\n\nСделай селфи в полный рост у зеркала. На фото должна быть видна форма: чистый фартук, бейдж и сменная обувь. Одежда чистая, опрятная, голова расчёсана.",
  "type": "photo",
  "section": "Начало смены",
  "ai_rule": "На фото сотрудник в форме: фартук и/или бейдж, сменная обувь. Форма чистая и опрятная.",
```

## Логика «⏸ Вернуться к пункту позже» (defer)

Реализована 2026-05-15. Полный дизайн-документ:
`memory-bank/creative/creative-defer-button.md`.

### Когда работает

- Только роль `manager` (см. `canRoleDefer` в `src/bot/index.ts`). Для всех
  остальных ролей кнопка скрыта на уровне UI и отвергается на уровне action.
- Лимит откладывания одного пункта = **1 раз** (`MAX_DEFER` в
  `src/services/runService.ts`). После исчерпания кнопка пропадает.
- Кнопка спрятана, пока идёт AI-проверка только что загруженного фото
  (`isPending`). Чтобы не оторвать фото от ответа, менеджер сначала выбирает
  «Да/Нет/Переснять», и только потом может отложить пункт.

### Поток данных

1. Менеджер нажимает «⏸ Вернуться позже» → `deferQuestion(runId, questionId)`.
   Если у пункта ещё нет `Answer` — создаётся placeholder
   (`value=''`, `checkResult=null`, `deferCount=1`, `firstDeferredAt=now`,
   `lastDeferredAt=now`). Если placeholder уже есть (теоретический случай) —
   обновляется. Финальные ответы (`checkResult != null`) защищены от повторного
   defer-а.
2. `getNextQuestion` исключает пункт из обычной фазы (`deferredIds`). Менеджер
   переходит к следующему обычному пункту.
3. Когда обычные пункты закончились, `sendCurrentQuestion` вызывает
   `getDeferredQuestions(runId)`. Если массив не пустой — рендерим
   `sendDeferredMenu` (стиль = меню выбора роли: столбец inline-кнопок, по
   одной на строку, ярлык `<№>/<всего> • <title>` с тримом до 60 символов).
4. Менеджер выбирает пункт в меню → `defer:resume:<runId>:<questionId>` →
   `getQuestionByIdForRun` → бот заново рисует вопрос как обычный, но кнопка
   «⏸» уже спрятана (лимит исчерпан).
5. Любой финальный ответ (`finalizeAnswer`, `recordManualAnswer`, `skipQuestion`)
   обновляет **тот же placeholder** Answer-а — таким образом `deferCount` и
   `firstDeferredAt` сохраняются как «след» откладывания для аналитики, а пункт
   автоматически исчезает из `getDeferredQuestions`.
6. Чек-лист **не может быть завершён**, пока в меню остались отложенные:
   `sendCurrentQuestion` всегда сначала проверяет `getDeferredQuestions`, и
   только если массив пустой — вызывает `completeRunAndSendSummary`.

### Хранение в БД

В `Answer` добавлены три поля (миграция `npx prisma db push`):

- `deferCount: Int @default(0)` — сколько раз пункт откладывали.
- `firstDeferredAt: DateTime?` — момент первого откладывания.
- `lastDeferredAt: DateTime?` — момент последнего откладывания.

Это надмножество: записи без откладывания имеют `deferCount=0` и обе даты
`null`. Старые записи через миграцию получают значения по умолчанию.

### Обязательный комментарий при пропуске

При нажатии «⏭ Пропустить пункт» комментарий теперь **обязателен**:

- минимум 5 символов (`MIN_SKIP_COMMENT_LENGTH`);
- placeholders `—`, `-`, пунктуация — отвергаются (regex
  `/^[—\-–_.,;:?!\s]*$/u`);
- бот просит реальную причину и подсказывает пример («нет ключей от склада»).

### Google Sheets — три новые колонки

`appendSingleAnswer` пишет в диапазон `A:Q` (вместо `A:N`). Новые колонки:

- `O` — `deferCount` (число, 0 если пункт не откладывали);
- `P` — `firstDeferredAt` в формате «дд.мм.гггг чч:мм» (пусто, если 0);
- `Q` — `deferStatus`: пусто / `Отложено → пройдено` / `Отложено → пропущено`.

Заголовки этих колонок нужно завести в шапке листов «Ресторан» и «Кофепоинт».

### Шорт-лист в конце чек-листа

`completeRunAndSendSummary` добавляет два новых раздела к итоговому сообщению
сотруднику и в чат менеджеров:

- `⏸ Отложено → пройдено (N): 1. <title>`
- `⏭ Пропущено с комментарием (N): 1. <title> — <комментарий>`

Оба раздела показываются только при наличии данных.

### Что НЕ нужно делать в коде

- Не вызывайте `prisma.answer.create` напрямую из bot-кода — всегда через
  сервисный слой (`saveAnswer`, `recordManualAnswer`, `skipQuestion`,
  `deferQuestion`). Эти функции корректно обрабатывают placeholder defer-а.
- Не показывайте кнопку «⏸» для не-менеджеров. Все клавиатуры строятся через
  `questionFooterRows` / `questionFooterRowsFor`, которые сами проверяют роль.
- Не разрешайте свободную навигацию по пунктам во время основной фазы — это
  было сознательно отброшено в дизайн-сессии 2026-05-15 (чек-лист = путь, а
  не каталог).

11. После правок чек-листы повторно загружены в БД через `npm run db:seed`, так что новая логика уже лежит в SQLite и готова к тесту в Telegram.

1. Утвердить логику для `Доступен всем` чек-листов Service Inspector

3. Проставить реальные `weight` / `can_skip` / `create_violation_on_no` в `src/config/checklists.json` там, где клиент это подтвердит
4. Подключить или донастроить эталонные фото и AI-правила
5. При необходимости добрать фото/историю из PDF-отчётов Service Inspector
6. Подключить выбранный AI-провайдер с ключом клиента
7. Деплой и финальное тестирование на сервере
